# Scoped iteration, independent review and handoffs

Use for substantial visual/interaction work. A tiny edit needs a small check, not this entire process. Foundation-only tasks stop before production implementation. They may include authorized isolated image-to-code specimens that test the design system. When establishing the system, follow [calibration before product build](image-to-code.md).

## One useful loop

1. **Freeze the task baseline:** relevant Git revision, accepted image/version, controlling quotes, journey, observed failure and unchanged constraints. Inspect relevant upstream changes and ownership before choosing files.
2. **Make the next uncertainty visible:** a small comparison for unresolved styling, a state diagram for behavior, or a realistic image for a new visual family. Supply the actual baseline/reference images to image generation. Do not regenerate near-approved Home merely to follow an external skill's mandatory image count.
3. **Describe interaction depth:** use the component contract. A fresh scoped designer can enumerate meaningful states and recovery from one coherent journey; do not launch an agent per button.
4. **Build when authorized:** implement from the image/contract in the real framework using shared tokens and accessible primitives. Keep exploratory mock code out of a clean rebuild. Use real capability boundaries and synthetic data for verification.
5. **Inspect actual output:** capture the actual renderer at the baseline viewport; inspect hierarchy, type, spacing, palette, borders, icon scale and nested surfaces. Exercise the journey and failure/recovery. A generated image is a target, not runtime evidence.
6. **Get an independent critique when valuable:** one visual/craft or behavior critic per coherent uncertainty, with original constraints and evidence. Use actual Opus 5.5 for consequential design critique when available and an independent fresh builder/QA instance where useful. Verify the exact model from receipts; if unavailable, name the fallback rather than implying the requested model ran.
7. **Integrate and compare:** require a source/observation for each asserted violation. Separate taste proposal, product conflict, implementation bug and untested concern. Fix supported gaps, inspect again, keep the best verified candidate. Check one affected sibling and the return path for regressions.
8. **Publish a compact outcome:** decisions changed, image/version, behavior evidence, remaining limits and ownership. Update canonical rules and examples, not an ever-growing parallel transcript.

Default refinement budget: two focused repair rounds, then reassess the unresolved failure. Continue if a new test distinguishes causes; stop polishing when evidence no longer improves or only a consequential human preference remains. This is a feedback checkpoint, not permission to stop required work or mark failure complete. Do not turn judge scores or pixel similarity into the objective.

## Human checkpoints and asynchronous work

- **First meaningful extension:** new visual family, major new surface or desktop-to-website translation. Show a concrete representative artifact and ask only about the unresolved decision.
- **First complete coded journey:** show default entry, meaningful action and return/recovery; request taste/workflow correction before broad replication.
- **Material deviation or release review:** ask when changing an accepted decision, resolving conflicting people, or a remaining choice changes the demo's core experience.

Reuse existing approvals; the 95% Home is already the first visual anchor. Do not re-gate every icon, token or repair. Batch one or two consequential questions with concrete choices. Continue unaffected research, implementation and provisional reversible variants while awaiting input. Do not commit dependent decisions as accepted without an answer.

## Small packet for a fresh agent

Provide only:

- Objective/audience and one complete journey; expected output and scope.
- Baseline commit + relevant file paths + image; exact controlling quote excerpts with scope/status.
- Owned files or read-only role; shared contracts/adjacent worker changes that matter.
- Required states and evidence; unknowns and unavailable capabilities.

Request: `findings → evidence → change/proposal → checks → unresolved human choice`. Start with a concise packet (roughly a page); link supporting details instead of loading transcripts. Size is a guide, not a cutoff that drops a critical constraint. Reviewer context omits the creator's preferred conclusion. Builders and critics get separate contexts when independence improves judgment. The driver integrates and verifies; two agreeing models do not establish correctness.

## Driver and dependency structure

Ben wants the active design conversation to drive the process: retain shared intent, route work, reconcile evidence, expose human decisions and integrate. Delegate coherent production/review leaves when available slots and independent ownership make them useful. Workers may delegate a genuinely independent leaf if the harness permits it; nested workers share the same runtime capacity. Do not claim unlimited parallelism or launch extra processes to evade a limit.

The critical path is a small agreed baseline/contract → parallel feature or platform work → integration → whole-journey verification. Reference investigation, asset/token packaging and independent contract critique can proceed concurrently. A feature does not wait for every decorative detail: freeze the shared semantics and accepted visual roles, then refine through shared tokens. Work needing an unresolved human decision can produce provisional alternatives while unrelated leaves continue. Do not give every worker the entire objective to independently rebuild.

## Keep parallel work safe

At startup, before shared-interface changes, and before integration/push, inspect relevant updates. Use natural boundaries every few minutes during sustained work; no timer loop, hooks or automatic merges. Record a short file/contract claim in existing team coordination while it is active; branch names do not establish ownership. Use isolated checkouts for overlapping edits, scoped additive modules for independent features, and one agreed integrator for shared shell/tokens/contracts. Ownership remains a proposal until teammates confirm.

If another worker changes the baseline, re-evaluate only affected contracts/states and their immediate siblings. Refresh the packet, supersede stale advice, preserve unrelated verified work. Reconcile staged scope before committing; never absorb other people's edits. Do not force push to resolve design drift.

## Use corrections as executable review criteria

Example: Ben says time text should match surrounding prose. Update its recipe and token binding; inspect an actual wrapped briefing line at normal and enlarged text; give the next critic that quote and screenshot. Merely appending “consistent type” to memory is insufficient.

For current correction gates, inspect the [governing accepted rules](../../../../DESIGN.md#accepted-corrections-that-govern-current-consumers) and [copy/label constraints](../../../../docs/design/content-design.md#current-copy-and-label-constraints). Audit source → projection → UI, compare actual Home color/density with the original anchor, and exercise empty/partial/stale schedules. Scan authored UI copy and inspect raw-source display separately. Keep noncompliant consumers pending; preserve existing typography, geometry, focus and evidence gates.

Maintain lightweight evidence records: requirement ID → affected component/path → relevant state → actual screenshot/test/observation → result/limit. Leave only unresolved or high-value regression cases active. Remove stale instructions rather than stacking contradictory amendments. Keep raw chats, X captures, private coursework and local research outside commits.

## Reference-driven specialist checkpoints

Ben explicitly requests periodic handoffs to Opus to refine the system through reference-driven design. Use meaningful boundaries (new family, supported correction, first transfer), not a timer or a review per edit. Give the reviewer one named gap, relevant exact user excerpts, Home/component images, the applicable source adapter and its pinned primary mechanism, and actual implementation/state evidence. Ask which rule should change, what output it changes, and how to test/reverse it. Read the source sufficiently to verify the recommendation rather than promote the reviewer's authority. Keep user taste and product intent controlling. Record actual model identity; browser or framework behavior still requires direct verification. This produces bounded rule improvements, not ever-growing expert commentary.

### Source fidelity and live specialist tests

At a meaningful source-driven audit checkpoint, give a critic the actual applicable upstream text (pinned copy or exact section), not only our paraphrase. Record which sources were read and which advice was excluded or adapted. A skill's popularity or author's reputation is a reason to inspect its mechanism, not authority to override Ben's accepted language. Select a coherent source family per reviewer; a separate reviewer is useful for a deep interaction uncertainty, not automatically per skill.

Separate code/image critique from browser testing. Use fresh scoped test workers for visual consistency, state recovery and adversarial content when those are independent uncertainties. Give each the normal entry, synthetic evidence, constraints, test boundary and its own browser session; keep repo edits with the integrator. Require actual model receipts when Ben asks for Opus, fresh runtime evidence and explicit untested limits. A process exit or `success` wrapper with no useful output is a failed review. Narrow a failed handoff and retry the affected boundary; never count it as corroboration.

For text/interaction robustness, challenge long names and unbroken tokens, increased text size, many items, interrupted actions, stale responses and hidden-tab feedback. These are proposed test inputs, not product copy. Fix the actual failure, then check an affected sibling. Retain useful failure cases; avoid shipping the entire research corpus into every agent context.
